# M0 results: limitations

Read this before quoting any number from `results/m0/table.md`. M0 is a
pipeline-validation experiment (ADR-0006). It demonstrates the expected
pipeline behavior and measures the gateway effect under a calibrated
simulator. It does not measure real-world LLM-agent security efficacy.

## The headline result is correct but expected

ASR drops from ~95% (vulnerable) to ~0% (protected) because a static denylist
blocks the sink names on the denylist. That is the design, not a discovery. The
Tier-1 gate has no ability it did not already encode in `sink-denylist.ts`. Do
not round this to "AegisMCP stops LLM agent attacks."

## The five family rows are identical by construction

`trust_probability` is a single global constant, so compliance depends only on
the seeded draw. Two families share the `fs.rm` sink and the other sinks are
one-per-family, so every row collapses to the same numbers. Differentiating
families is M1 work, not a reason to redesign the simulator (memory #137).

## FP = 0% is structural

Clean fixtures deliberately use sinks outside the denylist, so a false block is
impossible by construction. Treat FP = 0% as a regression invariant that proves
the runner wires clean controls correctly, not as evidence about real benign
traffic.

## `trust_probability` is a calibration knob

p = 0.8 is a parameter of the simulator, not an empirical estimate of how often
a real model trusts a poisoned tool response. Only M1, with a real LLM, can
attach a behavioral meaning to that number.

## n = 20 intervals are pipeline-validation uncertainty

The Wilson intervals in the table describe the simulator's variance. They are
not publication-grade confidence bounds.

## `traces.jsonl` is not byte-reproducible; `table.md` is

A commit cannot contain its own SHA, so the `git_sha` field in each trace is
always the parent commit. Regenerating traces after a commit rewrites all 300
lines. The table has no SHA column, so it is byte-stable.

`m0-table.test.ts` enforces two equalities: the table recomputed from the
committed `traces.jsonl` must equal the committed `table.md`, and the table
regenerated by running the code (`runAll()`) must equal the committed
`table.md`. Together they mean the committed traces must reproduce from the
committed code, so editing the sink list without regenerating traces, or
fabricating traces, fails CI (the shipped data matches code output
byte-for-byte). Judge reproducibility on the table, not the raw trace file
(memory #139, #140, #143).

## Gate and oracle share one source of truth

Both the Tier-1 gate and the oracle import `isDenylisted()` from
`sink-denylist.ts`, and `policy_version` is the content hash of that file. If
they diverged the measurement would be invalid; they cannot, by that single
export (memory #100).
